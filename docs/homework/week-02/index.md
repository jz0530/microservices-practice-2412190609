## 项目选题

### 最终项目名称

校园二手交易与担保履约平台

### 业务背景与目标用户

学生在毕业、搬宿舍或更换学习用品时，经常需要转让教材、数码配件和生活用品。通过群聊交易时，商品是否已经售出、双方是否完成交付、订单是否结束等信息容易分散，出现争议时也缺少统一记录。本项目面向校内学生及平台管理人员，通过商品发布、下单、校内面交和模拟担保结算，建立可查询、可追踪的交易过程。

主要目标用户包括希望转让闲置的学生卖家、希望购买闲置的学生买家，以及负责审核和处理纠纷的平台管理员。学生使用同一账号即可参与买卖，不需要分别注册两套账号。

### 选题理由与确定过程

选题过程中比较了宠物医院管理、餐饮点餐、场馆预约和校园二手交易等方向，重点讨论了宠物医院与校园二手交易两个方案。宠物医院业务丰富，但需要理解诊疗、药房和收费之间的专业规则。校园交易场景更熟悉，可以从一条完整交易流程开始，逐步增加异常处理和服务化能力，因此最终确定校园二手交易与担保履约平台，作为本学期唯一持续演进的课程项目。

该题目不仅包含商品信息管理，还涉及同一商品的并发购买、未付款超时取消、模拟付款与取消竞争、重复放款防护和结算前纠纷处理，能够支撑后续数据库、认证权限、消息、事务一致性、监控和部署等课程任务。

### 项目初步边界

本学期限定为单校园、学生个人闲置、固定价格、一笔订单一件商品、校内面交和模拟资金。第一版优先完成正常交易闭环，再补齐审核、超时取消和简单纠纷。纠纷仅允许在结算前申请，管理员只能裁决全额退款或全额放款。

暂不实现真实支付、真实身份认证、通用钱包、物流、拍卖、跨校交易、实时聊天、推荐算法和信用评分。评价与收藏仅在时间充裕时加入。这些边界使项目能够先形成可演示成果，再围绕已有业务逐步演进。

## 功能规划

### 用户角色与需求

| 角色 | 主要需求 |
| --- | --- |
| 学生卖家 | 发布和下架自己的闲置商品，查询销售订单，标记可交付，提交纠纷说明 |
| 学生买家 | 浏览商品、下单、模拟付款、确认面交完成，查询自己的订单并申请纠纷 |
| 平台管理员 | 审核商品、处理结算前纠纷、记录裁决理由，管理账号状态并查询操作记录 |

后端校验用户是否有权访问相关商品、订单和纠纷。管理员不能处理自己的交易纠纷。

### 功能模块与核心业务流程

| 模块 | 规划内容 |
| --- | --- |
| 用户与权限 | 注册登录、密码安全存储、角色权限及本人资源访问控制 |
| 商品与审核 | 商品发布、分类、图片、列表详情、上下架及审核理由 |
| 订单与面交 | 下单占用商品、查询订单、卖家标记可交付、买家确认完成 |
| 模拟担保结算 | 订单模拟付款、担保记录、放款及重复操作防护 |
| 取消与纠纷 | 未付款超时取消、释放商品，结算前暂停放款及全额退款／放款裁决 |
| 通知与审计 | 订单状态站内通知、失败重试和关键操作记录 |

正常流程：卖家发布商品 → 审核通过并上架 → 买家下单并占用商品 → 模拟付款进入担保 → 卖家标记可交付并完成校内面交 → 买家确认完成 → 模拟放款并完成订单。

异常流程：未付款超时则取消并释放商品；已付款但未结算时，可申请纠纷暂停结算，由管理员记录理由并裁决全额退款或全额放款。付款后退款不自动重新上架商品，需卖家核实实物情况后重新发布。退款与放款不得重复执行。

完整流程图、关键业务规则和计划验收场景见[根目录 README](../../../README.md)。

消息用于订单通知及跨模块协作；事务与幂等机制用于商品占用和模拟资金一致性。若时间不足，优先取消评价、收藏、统计和界面美化，保证核心闭环与课程必需任务。聊天、推荐、拍卖及跨校交易等仅作为远期方向。
